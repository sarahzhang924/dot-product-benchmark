# dot-product-benchmark

同一道点积（Scaled Dot-Product 的最后一跳）在 Python、C、Rust 三种语言里各写一遍，
用统一的计时协议对比耗时，并记录 AI 辅助写代码时踩过的坑。

2026 秋《数字媒体程序设计》第 04 讲实验作业。

## 测试数据

三语言用同一个线性同余生成器（LCG）与同一个种子生成数组，保证逐位相同：

```
seed = 42
seed = (1103515245 * seed + 12345) mod 2^31
a[i] = seed / 2^31
```

规模取 N = 10⁴、10⁵、10⁶。三份代码算出的校验和完全一致，说明喂进去的是同一组数：

```
N=10⁴    checksum = 2494.989707728
N=10⁵    checksum = 25014.748569889
N=10⁶    checksum = 250206.800394823
```

## 计时协议

- 预热 1 轮（结果丢弃），正式计时 5 轮取**中位数**
- 计时窗口只包住求和循环，数据生成、内存分配、打印都在窗口之外
- 结果必须被使用（打印成校验和），否则 -O2 会把整段循环优化掉

## 实测结果

在 OnlineGDB 上跑出来的中位数（2026-11-14）：

| 规模 N | Python | C（-O2） | Rust | 加速倍数（C / Python） |
|---|---|---|---|---|
| 10⁴ | 0.580 ms | 0.031 ms | 0.087 ms | 18.7 倍 |
| 10⁵ | 5.818 ms | 0.307 ms | 1.040 ms | 18.9 倍 |
| 10⁶ | 61.544 ms | 2.719 ms | 9.122 ms | 22.6 倍 |

规模越大，Python 落后越多——它的慢来自每个元素都要过一次解释器，是随规模线性付出的固定成本。

## 关于 Rust 那一列

Rust 比 C 慢 3.4 倍，这不是 Rust 的问题：OnlineGDB 给的 Rust 默认按 debug 构建（没开优化），
而 C 是手动加了 `-O2` 的，两边不在同一档。本地用 `rustc -O` 编译，Rust 应与 C 同量级。
比较不同语言时，先确认编译配置对等——这是本实验最值钱的一条教训。

## 文件

| 文件 | 说明 |
|---|---|
| `dot.py` | Python 版，`time.perf_counter()` 计时 |
| `dot.c` | C 版，`clock()` 计时，需 `-O2` |
| `dot.rs` | Rust 版，`Instant::now()` 计时 |
| `test_dot.py` | 5 个边界用例：n=0 / n=1 / 长度不匹配 / 全零向量 / 含 NaN |

## 怎么跑

- Python / C / Rust：打开 `https://www.onlinegdb.com`，左上角切换语言，粘贴对应文件，点 Run。
  C 要在顶部齿轮的 Compiler Options 里填 `-O2`。
- 边界用例：语言选 Python 3，粘贴 `test_dot.py`，点 Run，5 行全 PASS。

## 踩过的坑

1. **结果被优化掉**：C 版把 `res += a[i]*b[i]` 误写成 `res = a[i]*b[i]`，没有累加，
   `-O2` 判定整段循环无副作用直接删除，耗时趋近 0、校验和也变了。修法是把结果打印成校验和。
2. **三语言各算各的随机数**：数据不同，比的就不是同一个东西。改用同一个 LCG 与固定种子。
3. **计时把数据生成也算进去**：N 小的时候生成开销盖过计算本身，会得出「三语言一样快」的
   错误结论。计时窗口只包住求和循环，并且预热后取中位数。
